Kara — Stage 3: System Tray & Window Lifecycle

Implementation
- Normal launch shows Kara. Use libcosmic's run_single_instance launcher
  (the feature was previously enabled, but the regular launcher was called).
- A small zbus integration exports org.kde.StatusNotifierItem at
  /StatusNotifierItem and com.canonical.dbusmenu at /MenuBar, on libcosmic's
  existing activation connection. No second bus service/runtime is introduced.
- The system theme's view-list-symbolic icon identifies Kara. The native tray
  menu contains exactly Open Kara and Quit. Activation and Open Kara restore
  the main window and request focus, using COSMIC's supplied activation token.
- Task/list models, persistence, dialogs, navigation and styling are unchanged.
  Saved changes remain automatic; backgrounding retains model and dialog drafts.

Window lifecycle
- The current Wayland backend does not implement window visibility toggles.
  Use the existing public window close/open and Core::set_main_window_id APIs,
  with libcosmic's already-enabled multi-window daemon runtime. No dependency
  patch, desktop installation or application architecture replacement is needed.
- Intercept both the COSMIC titlebar close action and compositor close requests.
  When the tray is ready, destroy only the window surface; retain the app model,
  storage lock, subscriptions and session-bus activation service.
- Open restores an existing window or recreates one with the same application
  ID and native decorations. Wait for closure before reopening if requests race;
  repeated open requests cannot create multiple windows.
- Quit closes the activation/tray bus connection (up to one second), then uses
  iced::exit. Dropping the app releases storage locks. Unsaved dialog drafts are
  discarded on Quit; accepted task/list changes were already saved.
- Repeated launches use libcosmic's supported action arguments to retain the
  launcher activation token until a recreated window is ready. This avoids
  libcosmic consuming the standard platform token before the activation hook.

Tray availability and recovery
- Backgrounding is disabled until registration, watcher host availability and
  a connected client reading Kara's tray metadata have all been confirmed.
  Closing with no confirmed tray quits instead of leaving an orphan process.
- Check every two seconds, with a two-second timeout. Check watcher owner,
  registered items and host state without stale property caches; re-register
  after owner changes or lost registration. A hidden window is restored when
  checks fail, normally within two seconds (up to four for an unresponsive bus).
- COSMIC's watcher currently reports HostRegistered=true unconditionally.
  Therefore also observe property requests to our own tray item and verify
  consumer unique bus names remain connected. Applet loss is detected even
  when the separate watcher daemon remains alive. Host return is detected
  when the applet reads Kara's icon again; application restart is unnecessary.
- Failures produce a tray-status message in the window. While registration is
  pending, closing also quits safely. Existing task UI/dialogs are not redesigned.

   remains, and left-clicking the tray restores/focuses it with the same state.

   Repeat several times, including rapid close/activate clicks.

Known limits
- Session D-Bus and the enabled libcosmic single-instance path are required for
  tray/background operation. Without that connection (or if explicitly disabled
  using COSMIC_SINGLE_INSTANCE), the app remains a normal visible application
  and closes by exiting; libcosmic's fallback cannot provide D-Bus activation.
- Full session-bus restart is not reconnected by this libcosmic activation API.
  The window is restored on connection loss; close and relaunch to reconnect.
- A metadata consumer is evidence of a host connection, not proof of rendered
  pixels. A host that stays connected but deliberately stops displaying icons
  cannot be detected reliably through SNI. Hidden overflow icons still count.
- Focus is compositor-controlled. COSMIC tray/launcher tokens are used when
  supplied; tokenless clients get a token request/focus or attention fallback.
- Reopening creates a new surface; original compositor geometry is not promised.
- No implementation blocker found in the current libcosmic public lifecycle API.
  Actual CachyOS tray/rendering/window behavior still requires the checks above.
