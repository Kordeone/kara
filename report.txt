Kara — Unified Priority and Eisenhower Classification

Delivery

  headless Debian; the owner must accept the controls/colors on CachyOS.

Authoritative model
- Task.priority is the sole classification field, serialized as integer 0..3:
    P0 = Not Important & Not Urgent (new-task default)
    P1 = Not Important & Urgent
    P2 = Important & Not Urgent
    P3 = Important & Urgent
- Task no longer has matrix_quadrant. Quadrant is only a computed view/migration
  vocabulary with an explicit one-to-one mapping; it cannot diverge from priority.
- Invalid, fractional, missing or nonnumeric v4 priorities are rejected. Due dates
  never infer or change priority. Stable IDs and all unrelated properties remain.
- Normal Inbox/list creation defaults to P0. Matrix Add supplies that quadrant's
  priority and selected list, using the existing shared dialog and defaults.
- The accepted editor keeps its structure/date picker/validation. Its priority
  row now has four 36px native P0/P1/P2/P3 buttons, selected/focus states and
  tooltips/accessibility names explaining importance and urgency.

Matrix and presentation
- Removed Unassigned, its disclosure state and the separate bottom panel.
  All selected Inbox/list records appear exactly once among the four quadrants.
- Existing responsive 2x2 sizing, independently scrolling task regions, fixed
  headers/Add buttons and narrow/short viewport fallback remain in place.
- Reclassification writes priority. Editor priority changes follow the same
  append rule. Manual order stays scoped to (list, priority); ranks normalize
  stably without rearranging the shared task vector or sorting the Tasks view.
- List moves retain priority and append at the destination; deleting a list
  moves tasks to Inbox in prior relative Matrix order. Completed tasks retain
  priority/list, remain muted/struck through after active tasks, and are reversible.
- Small semantic P markers use COSMIC palette red (P3), blue (P2), yellow/amber
  (P1), and neutral gray (P0). The hues are subdued toward theme foreground and
  adjusted for 4.5:1 contrast against standard native surfaces. Full backgrounds
  keep their native theme styling. No custom theme or hardcoded color palette.

Explicit persistence migration
- Reads legacy schema versions 1, 2 and 3 through strict typed legacy records;
  reads/writes unified schema version 4 through strict numeric-priority records.
- Valid old Matrix classification takes precedence over old Low/Normal/High.
  Every previously unclassified task becomes P0, INCLUDING formerly High and
  Normal tasks. Old High does NOT imply urgency or importance. Those old values
  remain recoverable in the complete original-file backup described below.
- Every title, ID, due date, note, completion value, list ID, list name and pin is
  preserved. Existing Stage 1 reserved-list recovery remains. Legacy classified
  relative ordering is preserved and normalized; formerly unclassified records
  append after existing P0 records within their active/completed group, using
  original document order for ties. No records are duplicated or dropped.
- Opening a legacy file only converts/normalizes in memory. It does not rewrite
  tasks.json or create a backup. The first successful task/list mutation writes
  schema 4 only after a recoverable original backup has been published, read back
  byte-for-byte and synced along with its parent directory.
- Normal storage paths:
    ${XDG_DATA_HOME:-$HOME/.local/share}/io.github.kordeone.Kara/tasks.json
    same directory/tasks.json.pre-priority-v4.bak
  XDG_DATA_HOME must be absolute; existing fallback rules are unchanged.
- Backup is a 0600 temporary file, synced and published without clobbering an
  existing backup. A matching regular backup is verified/reused after a retry;
  a different file, symlink, directory, read/write/sync failure blocks migration
  visibly. No existing backup is overwritten. Resolve a conflict by preserving
  both originals elsewhere and inspecting them before retrying; do not delete
  an unknown backup to bypass the error.
- Existing storage lock, external-change checks, synced temporary saves and
  atomic replacement remain. The destination is rechecked after backup work.
  Failed pre-replacement writes leave disk and live records unchanged. Existing
  post-replacement durability warnings still distinguish already-written data.
- Interruption before replacement leaves legacy data plus a reusable exact
  backup; after replacement, restart reads whichever complete version the
  filesystem retained. The verified original backup remains available. No migration journal or database is needed. Repeated v4 opens/saves
  do not remigrate, change IDs or replace the original backup.
- Malformed/unrecognized versions, old priorities/quadrants, invalid ranks,
  duplicate IDs, invalid dates, unknown fields and dangling list references are
  rejected without resetting or rewriting data. All migration tests use copies
  in temporary directories; no personal task data was opened or changed.

Recovery / downgrade
- Keep the backup indefinitely if old priority significance matters. Old Kara
  binaries cannot read v4. The backup contains the entire pre-migration state,
  including Low/Normal/High, but not edits made after migration.
- To inspect/recover: quit Kara through the tray, preserve both current tasks.json
  and the .bak file, then COPY the backup into a separate disposable XDG directory
  as tasks.json. Use an older binary to inspect the original values, or this
  binary to repeat migration. Never replace a newer personal file blindly with
  the backup; that would discard later edits. No restore command was run here.

Limitations
- No graphical acceptance is claimed. Theme/selected-state contrast, compact
  controls, text wrapping and nested scrolling need the owner's COSMIC review.
  Marker tests cover standard COSMIC light/dark/high-contrast surfaces; unusual
  customized themes still require visual review.
- Legacy unclassified priorities intentionally become P0, even High/Normal.
  Original priority information is recoverable from the pre-v4 backup only.
- Backup creation needs free space and a writable data directory. Failures block
  the save; the owner must resolve the storage issue rather than losing data.
- No Tasks sorting, Show Completed toggle, drag/drop, sidebar redesign,
  autostart, packaging or other module functionality was added.
