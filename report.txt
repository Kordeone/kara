Implementation
- A compact Backup and Restore button with an accessible name and tooltip
  beside About opens a native
  COSMIC dialog. Export and Restore use libcosmic's existing XDG portal save/open
  dialogs, respecting user-selected paths rather than hardcoded host locations.
- Export captures tasks, lists (including pins), priority, Matrix ranks, IDs,
  dates, notes, completion, creation timestamps and persisted sort/direction/
  Show Completed preferences. No separate Calendar/Matrix records are created.
- Portable .kara-backup files contain JSON: explicit Kara format identifier,
  backup_version 1, embedded task schema version 6, data and a SHA-256 checksum.
  The checksum covers UTF-8 compact serialization of the typed data in fixed
  struct-field order, retaining vector order. JSON indentation/key reordering
  does not affect verification. An independently generated Python fixture tests
  compatibility with the format rather than only testing our writer against itself.
- Full validation precedes restore confirmation: format/version, required fields,
  data types/ranges, unknown fields, task/list uniqueness, list references, dates
  and checksum. Inputs are bounded at 64 MiB. Plain tasks.json, incomplete,
  truncated, damaged and unsupported files are rejected without touching live data.
- Restore clearly states current/imported counts and that all tasks, lists and
  saved preferences are REPLACED, not merged. Only explicit Replace data proceeds.
  Canceling the file dialog/confirmation has no data effect. Existing unsaved
  editors cannot be displaced by opening Backup and Restore; task writes are
  disabled while its modal is open. Portal and file errors are visible there.
- Selected backup loading/export disk work runs off the UI thread. Closing the
  panel is disabled during its outstanding portal/file operation; Cancel in the
  native file chooser returns to the panel. Long messages scroll, keeping Close
  accessible. Normal keyboard controls and the accepted task editor are retained.
- Confirmed restore updates the same Store, refreshes preferences/navigation and
  returns to Inbox, avoiding stale list references or drag sessions. Tasks,
  Calendar and Matrix immediately see the same restored records.

Safety and recovery
- Existing task JSON remains schema 6. There is no RON migration/new database.
- Export stages a private file in the destination directory, syncs it, publishes
  without clobbering and syncs the directory. Choose a NEW .kara-backup filename:
  existing files (even backups), symlinks and directories are never overwritten.
- Before restoration, Kara creates a unique portable recovery snapshot in the
  live data directory: kara-before-restore-<random>.kara-backup. Its bytes are
  read back, fully validated, and both file and directory synced BEFORE live
  replacement. The recovery path is shown after success or a later failure.
- Recovery snapshots preserve the previously loaded logical document. Existing
  legacy migration still creates its separate byte-exact original .bak file
  before replacing legacy JSON; export alone never triggers a migration write.
- Restore uses the existing locked Store commit path: complete validation,
  Matrix normalization, expected-file checks, staged file sync, atomic replacement
  and directory sync. Failed pre-publication writes leave the old Store/file intact.
- If publication succeeds but durability confirmation fails, Kara attempts an
  atomic rollback through the same external-change checks. It never blindly
  overwrites a later external edit. A rollback failure is reported with the actual
  in-memory state and retained recovery path; UI preferences reflect that state.
- Recovery snapshots are not automatically deleted. They are ordinary portable
  backups and can be selected with Restore to undo a restore. Each further
  confirmed restore first saves another recovery snapshot.
- Tests use temporary directories only. Actual user task storage was not loaded
  or modified by development tests.

Known limitations and packaging considerations
- CachyOS graphical acceptance of Backup/Restore remains pending. No COSMIC,
  Flatpak or AppImage installation/testing was performed on Debian.
- Portal selection supports normal Linux and sandbox-granted local file URLs;
  the existing XDG data path follows the runtime environment, not executable or
  installation location. No packaging, permission or authentication changes.
- A portal backend is required. Filesystems/portal grants must permit staging,
  atomic no-clobber publication and sync. Otherwise export fails visibly; there
  is no unsafe in-place fallback. In particular, writable document-portal grants
  need graphical/sandbox acceptance testing; packaged compatibility is not proven.
- Only backup format 1 / embedded schema 6 is accepted. Legacy ordinary storage
  can be opened and exported through Kara's existing migrations; raw tasks.json
  is deliberately not treated as a portable backup file.
- Exports/recovery snapshots have a 64 MiB limit. Backups are plaintext, not
  encrypted or authenticated; SHA-256 detects damage, not trusted provenance.
- Export/restore require a successfully loaded Store with no outstanding storage
  error. A corrupt/unrecognized live file stays protected: resolve/preserve it
  manually before loading a Store; this milestone does not auto-repair it.
- If storage hardware prevents both commit durability and rollback, the durable
  pre-restore recovery file remains available and the error explains the state.
  Power-loss handling relies on atomic file replacement and the synced recovery
  snapshot; no real power-loss/hardware fault experiment was performed.
