Automatic backup behavior and locations
- Disabled by default; default interval PT6H. Supported durations are positive
  ISO 8601 fixed weeks/days/hours/minutes/whole seconds, including PT30M, PT6H,
  P1D, P1W and PT1S. One day means 24 elapsed hours; one week means seven days.
  Months, years, zero/negative values, subsecond intervals and malformed input
  are rejected visibly rather than assigned an ambiguous schedule.
- Data root: $XDG_DATA_HOME/io.github.kordeone.Kara/ (or existing
  $HOME/.local/share/io.github.kordeone.Kara/ fallback).
  Live document: tasks.json; lock: tasks.lock.
  Automatic archives: automatic-backups/auto-<random-id>.kara-backup.
  Ownership/creation-order catalogue: automatic-backups/index.json (versioned JSON).
- A process subscription checks once per second regardless of window visibility.
  Linux CLOCK_BOOTTIME includes suspend and is immune to wall-clock adjustments.
  Persisted last success determines restart catch-up. First enable without any
  success, overdue restart, or a future last-success time on restart triggers
  at most one immediate catch-up; the next interval starts from that attempt's
  successful completion, without replaying missed periods.
- Running deadlines use boottime; forward/backward wall jumps cannot create extra
  backups or stall them. After a failed attempt retry is delayed at
  least 60 seconds. Last success changes only after a verified archive and Store
  checkpoint. Retention errors do not trigger repeated catch-up snapshots.
- Runs while Kara is hidden in the tray, and with ordinary Settings open. Defers
  during manual file operations and Restore/Clear confirmation. Store operations
  are serialized by the application event loop and existing storage lock; there
  are no concurrent snapshots. No service, daemon or autostart runs after Quit.
- Uses the same SHA-256-verified portable JSON format as manual backups. Archives
  stage privately, sync and publish atomically without clobbering existing paths;
  file contents are verified before catalogue/checkpoint publication. Failed
  writes do not retire previous good archives or silently advance last success.
- Retains the latest 10 successful catalogue-owned archives in creation order,
  independent of filesystem timestamps or wall-clock changes. Only entries with
  matching recorded file identity (device/inode/change time), regular file type
  and valid backup contents can be removed. A manual export reusing a removed
  archive's name is preserved. Unknown files, manual exports, symlinks, recovery
  snapshots and backups outside this directory are never retention targets.

Clear All Data and recovery
- Separate destructive section. Explains replacement of tasks, lists and persisted
  preferences, including automatic settings. Exact typed CLEAR and a further
  button press are required. Cancel/Escape makes no destructive data changes.
- Uses the existing checked replacement transaction. Before any destructive write
  a complete recovery backup is staged, synced, read back and validated, then
  atomically published and directory-synced. Recovery failure aborts the clear.
- Recovery files are protected in the data root:
  kara-before-clear-<random>.kara-backup
  Existing Restore recovery files remain kara-before-restore-<random>.kara-backup.
- Clears tasks/lists and resets sorting/direction/Show Completed and automatic
  preferences to defaults in ONE atomic task document. It never recursively
  deletes directories or removes archive/export/recovery/migration files.
- UI immediately reflects the Store's actual state, returns to Inbox, resets
  stale task/list editors, drag state, selected scopes, Calendar selection and
  scheduler. Automatic backups become disabled, interval PT6H, last success None.
  Stale editor messages cannot save pre-clear tasks back into the empty Store.
- Atomic failures before publication preserve live data; post-publication sync
  failure attempts checked atomic rollback. Recovery remains available if rollback
  or storage durability fails. Restoring the recovery file recovers all task/list
  properties and saved preferences, including the former automatic settings.

Compatibility
- Storage stays JSON, now schema 7 for atomic automatic-preference persistence.
  Schemas 1–6 still load without a write. First write from schema 6 preserves a
  byte-exact verified tasks.json.pre-settings-v7.bak. Existing older migration
  backup names/safeguards remain; conflicts block the write rather than clobber.
- Portable writer uses backup version 2 / data schema 7, including automatic
  preferences. Version-1/schema-6 backups still validate their ORIGINAL checksum
  and upgrade only in memory, defaulting automatic backups to disabled.
- No new serialization format/database. Backup catalogue is local ownership
  metadata, not portable data; foreign archive paths/identities are not imported.
- Older Kara binaries cannot read new schema-7 documents/version-2 exports. The
  original migration backup and version-1 imports remain available for recovery.

Limitations and operational notes
- COSMIC graphical acceptance remains pending. No Flatpak/AppImage testing or
  packaging changes. Portal export/import needs the desktop file chooser backend.
- Keep the existing 64 MiB portable backup limit. Backups are plaintext and not
  authenticated/encrypted; SHA-256 checks accidental damage, not provenance.
- Export/restore/clear require a loaded Store without unresolved storage errors.
  Damaged/unrecognized live files remain protected, with no empty-default repair.
- Corrupt catalogues, replaced/damaged archives, denied deletes or sync errors
  stop retention visibly and may leave MORE than 10 files. Uncatalogued files
  left by an interrupted publication are preserved, never swept automatically.
  Copying/chmod-ing managed archives can invalidate ownership identity; those
  files are protected rather than silently deleted. No automatic backup cleanup
  is applied to manual exports, recovery snapshots or legacy migration backups.
- Local archive/checkpoint I/O is serialized with Store writes and may briefly
  block UI updates on slow storage/large documents. There is no task-data race
  or parallel automatic worker. Power loss is not physically tested; protection
  relies on staging, sync, atomic replacement and preserved recovery files.

   In the transferred source directory:
     cargo build --locked
     KARA_SETTINGS_TEST_DATA="$(mktemp -d)"
     XDG_DATA_HOME="$KARA_SETTINGS_TEST_DATA" cargo run --locked
   Reuse the SAME test directory on restart. Never test Clear on production data.
2. Verify Settings is immediately right of the sidebar toggle, with native size,
   hover/focus/tooltip and Tab access. Open its native drawer in light/dark themes,
   wide/narrow windows. Confirm module switching, Tasks editor/date picker,
   Calendar, Matrix, About branding and tray controls remain functional.
3. In Backup & Restore, export to a NEW .kara-backup path. Cancel save/open and
   restore confirmations; verify unchanged data. Confirm one restore and check
   all fields/preferences. Recheck corrupt backup rejection before replacement.
4. Enable automatic backups, enter PT5S and Apply for a short test. Verify first
   success/last-success display, then periodic valid archives under:
     $KARA_SETTINGS_TEST_DATA/io.github.kordeone.Kara/automatic-backups/
   Allow more than ten successes; verify ten owned archives plus index.json.
   Keep manual/recovery files and confirm none are removed. Do not edit index.json.
5. Type invalid/zero/negative/month durations; verify inline errors, retained input,
   disabled Apply and unchanged saved interval. Close/reopen Settings to see the
   previously saved value. Apply disable and verify backups stop. Re-enable.
6. Hide Kara by closing the main window; verify archives continue. Tray Open must
   work. Suspend/resume past PT5S: expect one catch-up then normal periodic saves.
   Quit fully, wait past the interval, restart with the same XDG directory: one
   overdue backup, no burst. Do not change system clocks just for this test;
   backward/forward clock behavior is covered with deterministic injected times.
7. Keep a manual chooser open across an interval: automatic backup should defer,
   resume after cancel/completion, and show any file error clearly in Settings.
8. Populate tasks/lists, priority, dates, notes, completion, pins, Matrix order and
   sort preferences. Open Clear All Data. Empty/lowercase CLEAR must not enable
   confirmation; Cancel/Escape preserves data. Type exact CLEAR, confirm, verify
   empty/default UI and automatic backups disabled. Verify ALL manual/automatic/
   recovery files remain. Fully Quit/restart and verify the empty state persists.
9. Restore the displayed kara-before-clear recovery file via Settings. Verify
   all previous records/preferences return without duplicate IDs. Remember that
   restoring enabled automatic settings can make one backup due again.
10. Validate interval and backup errors/long paths, scrolling and keyboard access
    in small windows. For future Flatpak builds verify user-granted document
    portal paths permit atomic staging/publication; unsupported grants must fail
    visibly with no unsafe in-place fallback. Local automatic/recovery files use
    runtime XDG data paths inside the sandbox, not executable or host home paths.
    AppImage launch directory must not change storage locations. Do not change
    sandbox permissions or install packaging during this milestone.
