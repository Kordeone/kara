1. Matrix root causes and measured changes
- Baseline task_row asked matrix::neighbor twice for every task. neighbor rebuilt
  and sorted its entire group each time. A 10k concentrated diagnostic sweep alone
  took 14.36s in this run; actual native layout median was 17.50s (audit: 20.5s).
- Drop destination converted ordered Task refs back to vector positions using a
  fresh linear search per row. One 10k concentrated validation took 282ms.
- All rows were built/laid out even inside scrollables. Fixing lookup complexity
  alone would still leave thousands of widgets, glyphs, callbacks and drop targets.

Implementation
- Row Up/Down flags now use adjacent references from the ONE preordered group,
  retaining completion boundaries and full-group neighbor semantics. The general
  keyboard neighbor function uses one allocation-free linear scan, not sorting.
- Destination constructs/sorts original indices directly; source-group reindexing
  also retains indices rather than cloning IDs and searching repeatedly. Only the
  affected ordering groups change. Stored document order/identities are preserved.
- Investigated locked iced List: it incrementally measures and virtualizes content
  but does not delegate native drag destinations/accessibility for these cards.
  Replacing the proven DnD path with it would require a disproportionate wrapper.
- Used bounded native pagination instead: <=50 task cards per quadrant; <=200
  total. Small groups keep their existing display. Large groups show Previous,
  Next and a native range selector (e.g. 1–50 of 10000) for direct page access.
  Every task is counted/reachable; no records are discarded or silently filtered.
- Pagination is ephemeral per (list ID/Inbox, quadrant), never persisted in task
  ordering/preferences. Headers/Add remain fixed; each page scrolls independently.
  Direct page selection resets its native scroll position to the top.
- Page-end drop slots target the NEXT hidden record within the same completion
  group. At an active/completed boundary they retain the existing group-append
  semantics. Quadrant background drops still append within the matching group.
- Create/edit/complete, classify, reorder and successful drops follow the affected
  task's destination page. Keyboard Up/Down crosses page boundaries correctly.
- Native drag handles, source feedback, neutral preview icon, destination highlight,
  insertion marker and existing clipped hit boxes remain. Page switching is
  disabled during an active drag; choose destination pages before starting it.

2. Nonblocking storage execution and ownership
- Added storage_job.rs: async native chooser plus tokio::spawn_blocking for expensive
  work. No external worker framework, database, daemon or new dependency.
- Export encoding/publication, import reading/validation/Add preview, Add, Replace,
  Clear, automatic backup/checkpoint/retention, destination probes and settings
  persistence/retention now execute outside the UI thread.
- Exactly ONE writable Store (and its original File lock/expected byte snapshot)
  moves into the operation future. UI keeps Store::frozen(), an O(1) Arc-backed
  tasks/lists view with no lock and no document-byte copy. It cannot commit,
  create a backup, clear data, inspect storage as a writer or prune archives.
- The writer returns on BOTH normal success and ordinary transaction failure.
  The existing validated atomic/recovery/rollback methods still do the work;
  no optimistic UI state is saved over the result. JSON/backup versions unchanged.
- Gate permits one operation at a time and issues monotonic IDs. Duplicated/stale
  completion messages cannot install a different Store or consume a result twice.
  Its completion mutex only takes an ALREADY FINISHED result once; no worker holds
  it and no UI code waits on a Store mutex, joins a thread or blocks on a future.
- While busy, task/list writes, conflicting manual jobs and automatic ticks are
  rejected/deferred. Read-only navigation remains available. Progress appears
  in native text, Settings and the confirmation dialog; completion paths/errors/
  added/skipped counts remain visible. Destructive confirmations cannot be canceled
  mid-transaction. Native chooser Cancel remains safe before a transaction starts.
- Quit/Close-without-tray while work is active is recorded and executed after the
  result arrives. Native background windows/tray subscriptions keep running.
  Automatic backups preserve unsaved editor drafts, defer during backup/import
  confirmations or an active drag, and keep boottime deadlines, retry delays, destinations and retention behavior.
- Add preserves preferences/current navigation/scheduler; Replace/Clear rebuild
  actual UI state and saved preferences. Config success/durability outcomes reset
  the scheduler using actual stored preferences, even if retention reports an error.
- Worker panic releases the writer lock and leaves the UI snapshot read-only with
  a visible storage error. Retry reopens the EXACT original Store path, never a
  different default XDG path. It refuses missing/corrupt task data instead of empty
  defaults, clears stale confirmations and reconstructs UI/scheduler from disk.
  A fresh empty store with no tasks.json after a panic may require restart; this
  conservative case never authorizes an empty overwrite of a previously known file.

3. Persistence and recovery invariants
- Live storage remains version-7 JSON; portable backups remain version-2 JSON
  with existing version-1/legacy migration compatibility and checksums.
- Recovery snapshot is published/verified/synced BEFORE Add, Replace or Clear.
  Existing write-failure rollback path stays active on the worker; the test fault
  is injected on that worker's own thread, not incorrectly on the UI thread.
- Stable task/list IDs, conservative existing-wins Add/conflict rejection, no-op
  repeat import, explicit Replace confirmation and exact CLEAR remain intact.
- Destination permission/unavailability checks, atomic no-clobber publication and
  catalogue ownership retention stay unchanged. Previous destinations, manual
  exports, unknown files, migration backups and recovery snapshots are not pruned.
- No cancellation handle interrupts a destructive transaction. Forced OS kills or
  power loss still depend on the existing atomic/sync/recovery design; physical
  crash testing was not performed. An archive/catalogue/checkpoint can leave a
  conservative extra/unindexed file on interruption, as documented in the audit.

7. Limitations and remaining packaging blockers
- Pagination is bounded presentation, not continuous virtual scrolling. Choose
  source/destination pages before a drag; switching pages during a native drag is
  intentionally disabled. Cross-page keyboard reorder and direct range selection
  remain available. No drag autoscroll/page-turn behavior was invented.
- While a Store job is active, record writes are temporarily disabled rather than
  queued. Read-only navigation/tray remains live. One job can wait for a native
  chooser; Quit is deferred until it is canceled/completed. There is no unsafe
  force-cancel of a running filesystem transaction.
- Ordinary task/list CRUD, Matrix drop commits and initial/retry document loading
  still use existing synchronous persistence. These can pause on large files or
  slow disks. This milestone removes the audited 1–2s BACKUP/IMPORT UI transactions;
  it does not claim every data operation or Tasks/Calendar rendering is asynchronous.
- Tasks/Calendar still eagerly build/scan their own collections; native rendering
  of extremely large task views may need later work. Unbounded individual notes/
  titles and the live document/64MiB backup resource budget remain audit items.
- Widget-ID cache pruning for deleted/churned records, cold startup/idle CPU/RSS,
  GPU frame timing and multi-day tray memory behavior remain unmeasured/future work.
- No packaging artifacts created. Prior audit blockers remain: invalid AppStream
  metadata/template provides ID, hardcoded build output paths, dependency advisory/
  license decisions, MSRV/toolchain/offline build policy, actual Flatpak persistent
  portal write grants/atomic sync/retention identity, and AppImage runtime baseline.
  No new dependency/security audit or blanket advisory clearance is claimed here.
- No COSMIC graphical verification, physical power-loss or live hardware performance
  measurements were performed on Debian. Owner acceptance is required before merge.
