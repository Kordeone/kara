Implementation
- Backup & Restore now has compact Export Backup and Import Backup buttons with
  bundled Tabler icons. Existing native portal save/open behavior is retained.
- Settings uses bundled settings.svg, a neutral native 32x32 button with a 16px
  glyph matching About, and an explicit bottom tooltip with an 8px gap. Its
  accessible name, focus behavior and drawer toggle are preserved.
- Automatic settings use an aligned toggle, ISO interval and Keep last fields,
  brief examples, inline validation, compact local last-backup time and one Apply.
- Keep last defaults to 10 and accepts integers 1–100. Invalid input remains
  visible without changing persisted settings. Apply saves preferences atomically
  and applies retention; subsequent automatic backups use the saved count.

Import modes and safeguards
- A validated selected backup opens Add / Replace / Cancel with a merge preview.
- Add preserves current preferences and existing records. Missing IDs are added;
  matching task IDs are skipped, with differing records reported as conflicts
  resolved in favor of existing data. Counts are shown before and after import.
- Existing list IDs with different case-insensitive names, or different IDs with
  the same case-insensitive name, block the entire Add. No task is mapped by list
  name or silently attached to a different list. Matching names/IDs retain the
  existing pin/name values and report differences. Invalid references are rejected.
- Add recomputes and validates its complete plan before writing. Existing task
  IDs, properties and relative Matrix ordering are preserved. Imported peers keep
  their relative Matrix order and append within the appropriate completion groups.
  Existing completed rank numbers can normalize when active tasks are inserted;
  Tasks document order and its sorting preferences are not changed.
- Add retains the current navigation context and automatic scheduler deadline.
- Replace has a second explicit destructive confirmation and retains complete
  replacement of tasks, lists and persisted preferences, including automatic
  settings. Cancel makes no document changes.
- Both mutating modes reuse the checked atomic replacement transaction: stage,
  sync, read/verify and publish a complete recovery snapshot BEFORE live data is
  replaced. Failed recovery prevents import; post-publication sync failure uses
  the existing checked rollback path. External edits/storage corruption block
  changes rather than overwriting an unrecognized document.
- Add recovery: kara-before-import-add-<random>.kara-backup in Kara's data root.
  Replace recovery: kara-before-restore-<random>.kara-backup.
  A repeated/no-change Add does not write data or create an unnecessary snapshot.
  To undo an import, use Replace with its pre-import recovery file.

Persistence, automatic backups and Clear All Data
- Storage remains schema-7 JSON; portable backups remain version 2/schema 7.
  Version-1/schema-6 backups and existing schema migrations remain supported.
- Retention is an optional automatic preference, defaulting to 10. Serialization
  omits that default to preserve checksums of existing version-2 backups. An
  independently generated legacy version-2 fixture verifies compatibility.
  Older binaries may reject the new nondefault retention field; do not downgrade
  without an appropriate older backup. No migration safeguards were changed.
- Data root: $XDG_DATA_HOME/io.github.kordeone.Kara/ or the existing
  $HOME/.local/share/io.github.kordeone.Kara/ fallback; live document tasks.json.
- Automatic archives: automatic-backups/auto-<random>.kara-backup, with an owned
  index.json catalogue. Retention targets only catalogue-owned regular files
  with matching recorded identity and valid backup contents. Symlinked directories,
  replaced/damaged archives and invalid catalogues cause visible failures.
- Manual exports, unknown files, protected recovery snapshots and migration
  backups are never retention targets. No recursive or broad file cleanup occurs.
- Scheduling code and semantics remain unchanged: while running, including tray
  hiding; boottime deadlines handle suspend and wall-clock changes; restart
  coalesces overdue periods to at most one backup; no daemon after Quit.
- Clear remains separately confirmed with exact typed CLEAR, verified recovery
  before destructive writes, atomic reset/rollback and stale-editor protection.
  It resets retention to 10, automatic backups disabled/PT6H, while preserving
  manual exports, automatic archives and recovery snapshots.

Known limitations
- No COSMIC graphical, Flatpak or AppImage verification on Debian.
- Conservative list conflicts require resolving names/IDs or explicitly choosing
  Replace; the importer never guesses list identity. Only the first eight resolved
  ID-conflict descriptions are displayed, with a remaining-count summary.
- Existing 64 MiB backup limit remains. Files are plaintext, not encrypted or
  authenticated; SHA-256 detects accidental corruption, not trusted provenance.
- Retention errors can leave more than the selected count. Uncatalogued archives
  left by interrupted publication are preserved; no unsafe sweeping is performed.
- File I/O remains serialized on the existing Store path and can briefly block
  UI updates for large documents/slow disks. Physical power-loss testing was not
  performed; atomic publication, synchronization and recovery remain the safeguards.
- Future Flatpak packaging must verify document-portal grants permit staging and
  atomic publication. Unsupported grants must fail visibly without an unsafe
  in-place fallback. Automatic/recovery files use runtime XDG sandbox data paths;
  archive paths/ownership catalogues are not imported. No packaging changes made.
