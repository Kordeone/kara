Settings layout
- Removed settings::section cards. Sections now use the drawer's existing surface,
  consistent native spacing/padding and two subtle theme separators.
- Export Backup and Import Backup share an equal-width horizontal row, use bundled
  Tabler icons and native flat text buttons. Folder choice and Apply are also flat.
- Native drawer header, Close, Settings icon/tooltip, focus and access are retained.
- Automatic backups has enable toggle, numeric Every field, unit selector, Keep
  last (1–100), destination/path picker, last-success status and one Apply button.
- Units: Seconds (s), Minutes (m), Hours (h), Days (d), Weeks (w), Months (M),
  Years (y). Lowercase m means minutes; uppercase M means calendar months.
- Schedule, retention, folder and Apply controls are disabled while off. The locked
  dropdown has no disabled API; when off, its current label uses a disabled native
  button in the same position. Event guards also reject disabled input messages.
- Enabling stages the configuration until Apply. Disabling immediately persists
  the off state, even if staged values or the destination are invalid. Other
  staged inputs are not saved by disabling. This avoids an invalid form trapping
  the scheduler in an enabled state.
- Apply needs valid amount/unit, valid retention, and a verified selected folder.
  It rechecks writability before persisting; failures leave live preferences intact.

Intervals and scheduling
- Positive whole-number intervals only. New configurations require at least
  60 seconds, up to 1,000,000 units, with calendar caps of 1,200 months/100 years.
- Fixed seconds/minutes/hours/days/weeks keep elapsed-time semantics. Days are
  24 hours and weeks are seven days, preserving previous ISO duration semantics.
- Months and years use the locked jiff calendar arithmetic in the local system
  timezone, anchored to last successful backup. Month ends constrain to the last
  valid date: Jan 31 + one month becomes Feb 28/29; Feb 29 + one year becomes
  Feb 28. Local wall time is retained across DST transitions when representable;
  the library resolves DST gaps/folds consistently. These are never approximated
  by 30-day or 365-day constants.
- Each next calendar interval is relative to its successful predecessor, not an
  end-of-month recurrence rule. After a Jan 31 -> Feb 28 backup, the next month
  is relative to Feb 28. Overdue execution anchors the next interval to actual
  success, not an unbounded sequence of missed schedule dates.
- Running deadlines still use Linux CLOCK_BOOTTIME, including suspend and avoiding
  repeated backups from wall-clock jumps. Restart computes a single remaining
  interval from persisted last success; overdue/future-timestamp cases catch up
  at most once. Failed attempts retain a 60-second retry delay. No background
  daemon runs after full Quit. Manual operations/import/Clear confirmations still
  defer automatic backups, and Store operations remain serialized.

Old and new backup-directory behavior
- OLD default (still used when no destination preference exists):
    $XDG_DATA_HOME/io.github.kordeone.Kara/automatic-backups/
  Fallback with XDG_DATA_HOME unset:
    /home/rapper/.local/share/io.github.kordeone.Kara/automatic-backups/
  XDG_DATA_HOME was unset in this execution environment. This path was established
  from source/environment; existing real user task/backup files were not inspected
  or modified for testing.
- NEW configurations: user chooses an existing folder with libcosmic's native XDG
  portal folder picker. Archives and index.json are stored directly in that folder.
  Choose a dedicated folder; an existing foreign/damaged index.json is rejected.
- Folder verification uses a uniquely named disposable private probe: create,
  write, sync, read/compare, delete, directory sync and catalogue validation.
  It never overwrites an existing file or invokes sudo/privilege elevation.
  Permission errors identify the path and ask for a writable folder.
- Absolute real directories are required; relative paths, files, final-component
  symbolic links, unavailable folders and invalid catalogues fail visibly.
- Verified at choice, reopening Settings, Apply and before automatic publication.
  A previously selected folder that disappears is NOT silently recreated. Existing
  archives remain untouched; scheduler errors are visible and retries are bounded.
- Changing destination does not copy, move or delete the previous folder's files.
  The saved last-success timestamp is retained; switching destinations is not an
  instruction to replay earlier backups immediately.
- Default retention remains 10, configurable 1–100. Pruning targets only the
  current folder's catalogue-owned automatic archives with matching recorded
  device/inode/change time, regular file type and valid backup contents. Manual
  exports, unknown files, protected recovery snapshots and previous destinations
  are never swept. Retention errors preserve uncertain files and may leave extras.

Compatibility, backup integrity and recovery
- Existing ISO strings remain the persisted interval representation. Existing
  fixed/composite/fractional-but-whole-second intervals load into equivalent
  number/unit controls. There is no eager data rewrite on load.
- Existing sub-minute intervals remain readable; runtime applies the 60-second
  safety floor without rewriting their saved text. The form shows a minimum
  validation error until a valid new interval is selected and Applied.
- Storage remains JSON schema 7 and portable backups remain version 2/schema 7.
  A new optional absolute destination field defaults to None and is omitted when
  absent, preserving existing version-2 checksum compatibility. Old version-1
  backups and all existing task-data migrations remain supported.
- Older binaries can reject calendar intervals/new destination fields; do not
  assume backwards loading in older executables. Migration backups remain protected.
- Destination is a preference, so Replace restores it and Add keeps the current
  destination. On another machine, an unavailable restored path fails safely and
  must be reselected. Foreign archive catalogues/ownership are never imported.
- Manual export, checksums, Add existing-wins/conflict handling, Replace explicit
  confirmation, verified pre-import recovery snapshots, atomic replacement and
  rollback are unchanged. Add no-ops do not rewrite documents or create snapshots.
- Clear still requires exact typed CLEAR, creates/verifies recovery first, aborts
  on recovery failure, resets all managed preferences (including destination),
  prevents stale-editor writes, and preserves manual/automatic/recovery files.
- Recovery snapshots remain in Kara's XDG data root, not the chosen auto folder:
    kara-before-import-add-<random>.kara-backup
    kara-before-restore-<random>.kara-backup
    kara-before-clear-<random>.kara-backup
  Restore these using Replace to undo a prior import/clear.

Limitations and portal considerations
- No COSMIC graphical or packaged sandbox verification was performed on Debian.
- The folder picker uses the locked native portal path/grants and persists its
  returned path. Kara does not change sandbox permissions or grant itself access.
  A read-only, revoked, nonpersistent or insufficient portal grant fails the access
  probe or later backup visibly; reselect the folder through the chooser. Persistent
  write access across actual Flatpak restarts must be checked when packaging.
- Portal/FUSE backends must support private staging, directory sync, atomic
  publication and stable identity for retention. Unsupported access fails safely;
  identity changes protect archives rather than authorizing deletion. AppImage
  launch directories do not change configured/XDG paths.
- A clock/timezone change does not revise an already cached running boottime
  deadline. The current local timezone is used for subsequent calendar calculations
  and for restart reconstruction. No fixed timezone/recurrence preference is added.
- Existing 64 MiB portable limit and plaintext/unencrypted backup format remain.
  SHA-256 checks accidental damage, not provenance. Local I/O is serialized and
  may briefly block UI updates on slow storage. Physical power-loss and hot-unplug
  races are not hardware-tested; existing atomic sync/recovery checks remain.
