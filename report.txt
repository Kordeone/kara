Matrix MVP

      Important & Urgent          | Important & Not Urgent

  Below it is an always-present Unassigned area. Content scrolls; below 720
  logical pixels of content width the quadrants stack in row-major order.
- Each task has a native classification dropdown, completion checkbox and

Model and ordering
- Optional task fields: matrix_quadrant and matrix_order (zero-based u64 rank).
  Quadrant variants explicitly encode ImportantUrgent, ImportantNotUrgent,
  NotImportantUrgent and NotImportantNotUrgent. Absence means Unassigned.
- Importance/urgency are never inferred from priority or dates.
- Ranks are scoped to (list ID or Inbox, quadrant), not list names. Other
  lists/quadrants may reuse the same rank. Classified ranks are normalized
  contiguously after accepted mutations and when loading into memory.
- Ordering is active first, completed second. Up/Down swaps neighbors inside
  the same completion group. Append means the end of the destination completion
  group, preserving the rule that completed tasks always follow active ones.
- Reclassification/list moves append at the destination and compact the old
  group. Unassigning clears rank. Completion moves a task into the completed
  group; reactivation appends to the active group without losing its quadrant.
- List deletion moves all its tasks to Inbox, retaining classification and
  relative Matrix order, after existing Inbox tasks in each completion group.
- Only Matrix rank fields change during reordering; shared document record
  order and Luna's existing Tasks presentation order are preserved.

Persistence compatibility and failure safety
- Same XDG tasks.json, lock, atomic replacement, synced writes and external
  conflict checks. No user task data was accessed during automated testing.
- Reads document versions 1, 2 and 3. Legacy tasks without Matrix fields default
  to Unassigned; existing list IDs, pins, task IDs and other task fields remain.
- Opening a file does not rewrite its bytes. Duplicate/gapped/missing classified
  ranks normalize stably in memory, with document order resolving ties. The
  next accepted write saves the entire document atomically as schema version 3.
- Unknown quadrants/fields, non-integer/negative ranks, an order without a
  quadrant, invalid records, dangling lists and unsupported versions block
  loading visibly and preserve the original file. No silent reset occurs.
- Failed writes retain the previous live data/ranks and disk contents. External
  edits block writes. The existing post-replacement sync-failure warning still
  explicitly distinguishes written data from uncertain durability.
- Older Kara binaries reject version 3. Use disposable/copied data for feature
  validation; do not downgrade an upgraded personal data file to an older app.
